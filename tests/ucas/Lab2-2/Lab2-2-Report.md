# Lab 2.2 Exploring Cache Behavior 实验报告

## 1. a) 配置脚本修改说明

使用自编配置脚本 `lab22.py`（以 `configs/learning_gem5/part1/two_level.py` 的结构为基础），
初始配置 = 手册要求：**O3CPU、1GHz、DDR3_1600_8x8、L1I 32KB/2-way、L1D 64KB/2-way、
L2 256KB/8-way、issue width 8**（O3CPU 默认 fetch/issue 宽度即 8）。

脚本暴露的参数（7 组实验只改以下参数，其余固定；缓存时序参数沿用 two_level.py
默认：L1 tag/data latency 2，L2 20）：

| 参数 | 取值 | 对应实验 |
|---|---|---|
| `--issue-width` | 8 / 2 | 发射宽度 8→2（O3 的 `issueWidth` 字段） |
| `--cpu-freq` | 1GHz / 4GHz | CPU 频率 |
| `--l2-size` | none / 256KiB / 2MiB / 16MiB | L2 有无及容量（none 时 L1 直接接内存总线，保留 L1） |
| `--l2-assoc` | 8 / 4 | L2 相联度 |

注：按手册表格，freq4 与 iw2 两组的"无 L2"组合仍保留 L1 缓存。

## 2. 基准测试程序设计

三个自编微基准（源码见提交文件，`gcc -O2 -static` 静态编译，输入内嵌，SE 模式无系统调用问题）：

| 基准 | 内容 | 工作集 |
|---|---|---|
| `bench_seq` | 顺序扫描 uint64 数组求和 | 64 MiB（8M 元素） |
| `bench_random` | xorshift64 伪随机下标 gather-sum（8M 次） | 64 MiB |
| `bench_gemm` | 64 分块浮点矩阵乘 384×384 | 活跃数据 ~100 KiB（分块片） |

### 四属性分析（Step3 问题 1）

| 属性 | bench_seq | bench_random | bench_gemm |
|---|---|---|---|
| Memory Regularity（访存规律性）| 高：地址严格 +8 递增 | 低：地址不可预测 | 中：规则嵌套循环，访存集中于分块片 |
| Control Regularity（控制规律性）| 高：无分支（实测分支预测错误仅 1,036 次）| 高：无分支（1,048 次）| 高：规则循环（236,553 次，但占 132M 指令比例极小）|
| Memory Intensity（访存强度）| 高：每元素 1 load | 高：每元素 1 load + 下标计算 | 低：高算术强度，每 ~12 条指令 1 次访存 |
| Memory Locality（局部性）| 差：64MB 无复用，仅 compulsory miss | 差：时间/空间局部性均无 | 好：分块片在 L1/L2 反复命中 |

### 指标佐证（Step3 问题 2，默认配置 stats.txt）

| 指标 | bench_seq | bench_random | bench_gemm | 说明 |
|---|---|---|---|---|
| `system.l1d.overallMissRate::total` | **56.2%** | **56.1%** | **5.2%** | 局部性的直接量化：Locality 好坏差 11 倍 |
| `system.l2.demandMisses::total` | 2,098,855 | 9,406,097 | 108,999 | L2 缺失绝对量：Random 的 L2 形同虚设 |
| `system.cpu.ipc` | 0.361 | 0.363 | **2.423** | 访存受限 vs 计算受限：IPC 差 6.7 倍 |
| `system.cpu.branchPred.condIncorrect` | 1,036 | 1,048 | 236,553 | 控制规律性（三者分支都可预测）|

**结论**：判断 Memory Locality 用 **L1D/L2 缺失率**最直接（5% vs 56%）；判断
Memory Intensity / 瓶颈用 **IPC 与缺失率组合**（低 IPC + 高缺失率 = 访存受限；
高 IPC = 计算受限）；Control Regularity 用分支预测错误率（本组三个基准都高，
区分度不大）。

## 3. 实验结果（Step3 问题 3）：simSeconds（越小越好）

| 基准 \ 配置 | base（L2 256K/8） | 无L2 | 无L2+4GHz | 无L2+iw2 | L2 256K/4路 | L2 2M | L2 16M |
|---|---|---|---|---|---|---|---|
| seq | 0.1629 | **0.1022** | 0.0746 | 0.1145 | 0.1629 | 0.1630 | 0.1638 |
| random | 0.3932 | **0.2642** | 0.2211 | 0.2643 | 0.3932 | 0.3876 | 0.3411 |
| gemm | 0.0545 | 0.0707 | 0.0358 | 0.1521 | 0.0546 | **0.0526** | **0.0526** |

（每个基准 58.9M / 142.7M / 132.1M 条指令，配置间指令数完全一致，时间差全部来自微架构。）

### 敏感度分析（问题 3）

**bench_seq（顺序流式）—— 对 L2 存在与否高度敏感（反直觉），对 L2 容量/相联度完全不敏感**
- L2 容量 256K→2M→16M：0.1629→0.1630→0.1638，**纹丝不动**：64MB 流式扫描全部是
  compulsory miss（L2 缺失恒为 2,098,855），更大的 L2 只能装"不会再访问的过去"；
- 相联度 8→4 路：同样无变化（每个地址只来一次，无冲突可消）；
- 去掉 L2 反而 **快 37%**（0.163→0.102）：见问题 4；
- 频率 1→4GHz（无 L2 组内）：−27%：指令执行占一部分，其余是 DRAM 等待；
- iw 8→2：+12%：扫描求和依赖链短，宽度减小影响有限。
- **瓶颈：DRAM 带宽/延迟，缓存无能为力**。

**bench_random（随机）—— 最彻底的访存受限：发射宽度零敏感，只有超大 L2 有一丝作用**
- iw 8→2：0.2642→0.2643，**完全无差**：每次访存都缺失（L2 缺失 9.4M ≈ 访问数），
  CPU 再宽也只是在等内存——教科书级的 memory-bound 证据；
- 频率 4GHz：−16%（CPU 侧开销压缩，DRAM 等待不变）；
- L2 2M：−1.4%（64MB 工作集，2M 命中率≈3%）；L2 16M：**−13.2%**（16M/64M=25%
  的行能在再次访问前存活）——容量终于开始起作用；
- 去掉 L2 快 33%（同 seq）。
- **瓶颈：访存延迟；解药只有容量达到工作集的可观比例**。

**bench_gemm（分块矩阵乘）—— 计算受限：频率和发射宽度是主宰，L2 是温和的加分项**
- 频率 1→4GHz（无 L2 组内）：0.0707→0.0358，**−49%**：几乎随主频线性——纯计算瓶颈；
- iw 8→2：0.0707→0.1521，**+115%**：分块内乘加链在窄发射下排队；
- 去掉 L2 慢 30%（0.0545→0.0707）：与 seq/random 相反——**L2 对它是有用的**
  （局部性好，L1D 缺失率仅 5.2%）；
- L2 256K→2M：−3.6%（L2 缺失 109K→29.5K，三个矩阵 ~1.7MB 全装进 2M）；
  16M 与 2M 完全相同（装下即饱和）。
- **瓶颈：执行吞吐（频率×宽度），访存已被分块算法解决**。

### 问题 4（可选）：反直觉配置——去掉 L2 反而提升性能？

**有，且非常显著**：seq **−37%**（0.163→0.102）、random **−33%**（0.393→0.264）。
原因：这两个负载对 L2 的命中率为 0（无复用），L2 在 L1 缺失路径上**只加了一级
~20 周期的查找延迟 + 总线跳数**，却换不到任何命中——纯负资产。这说明：
缓存的收益完全来自命中，没有命中的缓存只剩延迟；也解释了为何真实处理器
为流式负载设计了 bypass/非临时访问提示（如 x86 `movnt`）。对 gemm 则完全相反
（去掉 L2 慢 30%），"反直觉"只属于无局部性的负载。
